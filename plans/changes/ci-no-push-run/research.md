## What exists today

**The workflow is derived, and the trigger set lives in the generator.** `.github/workflows/ci.yml` carries the header "GENERATED by `python3 scripts/ci_gates.py --generate-ci` from decisions/gates.yaml (D-10). Hand-edits fail the ci-drift gate on purpose", and `scripts/ci_gates.py` (`check_ci`) compares the committed file byte for byte with `generate_ci()`. The triggers are written by `generate_ci` as literal lines: `push:` filtered to `branches: [main]` (the constant `MAIN_BRANCH = "main"` in `scripts/ci_gates.py`), a bare `pull_request:`, `merge_group:` with `types: [checks_requested]` (the comment there names the merge queue and bead coding-harness-eh42), `schedule:` with cron `"23 4 * * *"`, and `workflow_dispatch:`. Nothing in the trigger set comes from `decisions/gates.yaml`.

**Which jobs run on which event.** The matrix job `gates` runs under `if: github.event_name == 'push' || github.event_name == 'pull_request' || github.event_name == 'merge_group'` (`generate_ci`, the matrix-job condition), one leg per declared interpreter (`tools.python: ["3.12"]`, the only entry in `decisions/gates.yaml` under `tools`). The summary job `verify` (`_summary_job` in `scripts/ci_gates.py`) runs under `always() && (the same three events)` and passes only on `needs.gates.result == success`. The `drift` job runs only on `schedule` and `workflow_dispatch` and carries only the two `job: drift` gates of `decisions/gates.yaml` (`plans-registry-strict`, `research-currency`). Consequence recorded by tests: a `workflow_dispatch` run today runs only the drift gates — there is no on-demand hosted full verify (`tests/test_ci.py`, `test_the_schedule_runs_only_the_drift_job`, whose docstring says the matrix and summary jobs admit "never `schedule` or a manual start").

**A push run is never cancelled.** `concurrency.cancel-in-progress` is the expression `${{ github.event_name == 'pull_request' }}` and the group is `verify-${{ github.event_name }}-${{ github.ref }}` (`generate_ci`; the `job:` comment in `decisions/gates.yaml`: "A newer run of the same pull request cancels the older one; a push run is never cancelled"). `tests/test_ci.py::test_only_pull_request_runs_cancel_superseded_runs` holds both strings exactly.

**Tests that hold the push trigger and the event conditions** (`tests/test_ci.py`): `test_push_starts_the_workflow_only_on_main` asserts `trigger["push"] == {"branches": ["main"]}` for both the committed file and a fresh `generate_ci()`; `test_the_schedule_runs_only_the_drift_job` asserts the matrix and summary conditions as exact three-event strings; `test_the_summary_check_passes_only_when_every_leg_passed` requires `push` and `pull_request` in the summary condition and `schedule` absent; `test_drift_job_runs_on_schedule_and_dispatch_only` requires `push` to be named in the matrix job's condition and absent from the drift job's; `_einschraenkungen` and `test_the_trigger_does_not_restrict_paths` read the `push` and `pull_request` blocks for path filters (none allowed); the merge-group helpers (`_merge_group_findings`, `_plant_no_merge_group`, `test_merge_groups_run_the_gates_on_their_candidate`) hold the `merge_group` trigger, its `checks_requested` type, and that the gates run on the group's candidate, not a pull-request head.

**The ruleset asks for no push-run check.** `tests/test_repo_settings.py` (module docstring, RB-M6/RB-G7) holds: pull request required, the check `verify` required and pinned to GitHub Actions (`REQUIRED_CHECK = "verify"`, `GITHUB_ACTIONS_APP_ID = 15368`), no force push, no deletion, empty bypass lists, and freshness by strict up-to-date flag or an active `merge_queue` rule (`MERGE_QUEUE`). The queue asks the required check on each group's merge candidate; the in-tree merge procedure (`prompts/07-commit.md`, "The merge", steps 2–7; `docs/WORKFLOW.md` §3 "Merging a series, one at a time") reads the pull request's check rollup and merges through `gh pr merge <n> --merge --match-head-commit <sha>` — it never waits on a status of a `main` commit. Nothing found in `tests/test_repo_settings.py` that requires a check produced by a push run.

**One script hook is keyed to the push run.** `scripts/check_interview_minimums.py`, `_mainline_ci()`: `os.environ.get("GITHUB_REF") == "refs/heads/main"`. Its `_base()` uses it to pick the comparison base: on the main line — a genuine `main` checkout or the hosted main-line run — the base is the first parent (`HEAD^`); otherwise the merge base with `origin/main`; a detached HEAD at `origin/main` is NOT MEASURED (exit 3 through `CannotMeasure`). The docstring of `_mainline_ci` notes the derived workflow checks out a detached head (checkout is `actions/checkout@v4` without a `ref`, `_checkout` in `scripts/ci_gates.py`), which is why the branch name cannot speak in hosted runs and the `GITHUB_REF` environment carries the distinction. On a `merge_group` run today the checkout is the detached candidate containing `main` plus the pull request, so `_base()` takes the merge-base path and the gate measures the candidate's diff. This behavior is documented in `docs/WORKFLOW.md` §3, the table row "Interview": "compares per context — first parent on the main line (a `main` checkout or the hosted main-line run), else the merge base".

**Where the trigger shape is stated in prose.** `docs/WORKFLOW.md` §3: "CI runs on pull requests (a superseded run is cancelled) and on pushes to `main`, under Python 3.12; a branch without a pull request gets no hosted run, and the schedule runs only the drift gates." The `job:` comment of `decisions/gates.yaml`: "verify (per push to main / pull request) or drift (per schedule/dispatch)".

**Decision of record for the current shape.** The archived change `plans/changes/archive/2026-11-06-ci-minutes/spec.md` (bead coding-harness-cac, bounded) fixed the current trigger set: criterion 1 pins the push trigger to exactly `branches: [main]`, criterion 8 requires `decisions/gates.yaml` and `docs/WORKFLOW.md` §3 to say "a push runs CI only on `main`". Its research measured (maintainer, 2026-10-13, last 100 runs): 61 successful push runs against 8 pull_request runs, about 3.5 minutes each. The `merge_group` trigger was added by the archived change `plans/changes/archive/2026-11-06-merge-queue/spec.md` (bead coding-harness-eh42), whose problem statement notes the workflow accepted no `merge_group` event before.
