| S-1 | MAJOR | SPEC | base | spec.md criterion 3, Terms; decisions.md Q-1 | [AMBIGUITY] "An archive beside the state directory" can mean two places, because the spec uses "state directory" for two things. Terms use it for one worktree's `stage2/<change>@<digest>/`, while criterion 1 uses "the current state directory" for the base that holds every key. Reading A: the archive sits inside `stage2/` next to the key directories. It then shares the namespace that criterion 1's scan and the `--supersedes` key check read, so both have to skip it, and its name must not let a second supersession of the same key overwrite the first archive. Reading B: the archive sits next to `stage2/` in its own tree, where the scan never meets it. Criterion 3's test checks a path, so it depends on which reading holds. The accounting line in criterion 2 names only the key, so under neither reading do findings.md or the workflow (criterion 10) say how to find a given archive. | Opus | open | — |
| S-2 | MAJOR | SPEC | base | spec.md criteria 1, 2, 5; decisions.md Q-1 ("the audit calls it accounts for") | [AMBIGUITY] Which audit calls the line accounts for. Reading A: every review-loop audit line still pending in the current findings since the last release or restart, i.e. what `lost_record_refusal` counts. Reading B: only the calls that belong to the superseded record. Audit lines carry no key, so B needs an attribution rule the spec does not give. The two readings split when criterion 1 names two or more keys. Under A, superseding one key clears the refusal, the other record is never named again and stays active at its key. Under B, the refusal keeps firing until each record is superseded. The spec also does not say whether supersession is allowed when no call is pending. Criterion 5 lists no such refusal, so as written any worktree of the change could archive another worktree's idle record with a line that accounts for 0 calls. | Opus | open | — |
| S-3 | MAJOR | SPEC | base | spec.md criteria 2, 4, 9; docs/WORKFLOW.md "A release needs a `Phase 6 verdict:` line … after the last `Loop restarted:` line" | [AMBIGUITY] What kind of line `--restart --supersedes` writes. Reading A: supersession is a restart under the ADR 0021 amendment, so its one line is a `Loop restarted: <date> after round <N> — …` line. Every existing restart reader then applies to it: the verdict floor, the stop floor, `restarted_fresh` and the "already restarted" refusal. N has to come from a record that findings.md has never contained. Reading B: it is a new kind of line that only the lost-record check and round numbering learn about. Then release's floor (`max(last release, last restart)`) does not move, and a `Phase 6 verdict:` line already in findings.md before the supersession releases the new run's rows. That breaks the amendment's rule that a restarted run is released only after a new phase-6 verdict, and no criterion goes red. | Opus | open | — |
| S-4 | MAJOR | SPEC | base | spec.md criteria 5 and 7 | Hole: criteria 5 and 7 conflict for an interrupted supersession. Supersession writes in two places, findings.md in the worktree and the archive in the state directory, so it cannot be one atomic step. If the archive is moved first and the run stops before the line is written, the retry finds the key missing at its old place. Criterion 5 says a missing key must be refused with nothing changed; criterion 7 says the retry completes. If the line is written first and the run stops before the move, findings.md already shows a restart while the record is still active at the old key, which is criterion 7's "false completed restart". Avoiding that would need the current worktree's review-loop to look across keys, which Q-1 allows for one command only. The spec does not say which half-done state is allowed, how a retry recognises it, or whether "absent at the old key but present in the archive" counts as missing. It also does not say what observable state makes a "false completed restart" (exit status, a line in findings.md, or a fresh review-loop being let through), so that part of criterion 7 has no defined red case. | Opus | open | — |
| S-5 | MINOR | SPEC | base | spec.md criterion 1 | [AMBIGUITY] Which refusal criterion 1 means by "the missing-record refusal". Reading A: only `lost_record_refusal`'s message, used by review-loop, release-loop, `--stage-failed` and prepare-loop. Reading B: also the other no-record refusals. Those are `restart_loop`'s "has no completed loop round and its loop record is missing; the maintainer must account for the stale audit lines in findings.md by hand" and triage's "the change has no loop record here". Under A, the incident's own path (the maintainer trying `release-loop --restart --reason`, as L4's handover asked) still gets a message that names no key and sends them to the hand reconciliation this change replaces. Under B it names the keys. The tests for criterion 1 differ between the two. | Opus | open | — |
| S-6 | MINOR | SPEC | base | spec.md criteria 2 and 4 | [AMBIGUITY] What "its rounds" in the accounting line means. Reading A: how many round headings the superseded record has, e.g. "3 rounds". Reading B: which round numbers it holds, e.g. "rounds 4–6". They differ whenever the old record did not start at round 1 because the old worktree released earlier rounds. Under A, a new findings.md that lacks that earlier release gives a next round of 4, which reuses a number from the superseded record and breaks criterion 4. Criterion 2's "misstates" cannot be tested until one reading is fixed. The same is open for "the audit calls accounted for": a count, or the lines named. | Opus | open | — |
| S-7 | MINOR | SPEC | base | spec.md criterion 9; scripts/stage2.py `release` (no-record branch) | Hole: the spec does not say what release-loop does after a supersession when no new round has run. Today, `release` with no record and no released block in findings.md (exactly the incident's state after supersession) appends `Loop rows: none — the loop did not run for this change.` once a verdict line stands. Criterion 9 keeps that behaviour, so the runner would write a false line, which is the kind of untrue record Q-1 set out to avoid. The spec does not say whether release-loop should refuse in that state, write nothing, or write that line. | Opus | open | — |
