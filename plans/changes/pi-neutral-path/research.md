## What exists today

**The finding and its history.** The phase‑6 deep reviews of the research swarm (2026‑10‑25) recorded as their only open NIT (row RS‑3): Pi's own system prompt carries local paths, with the recommendation to install the pinned Pi at a neutral path for research launches and to add a capture check that no home or worktree path reaches an online model (`docs/journal/handover/2026-10-25-cloud-runner-fixes.md`, section "The research swarm repair in detail", row "Open, NIT: RS‑3"). The work became bead coding‑harness‑xul8 ("Pi sends no local paths"). The measurement behind it (handover 2026‑10‑29, `docs/journal/handover/2026-10-29-three-lane-night.md`, item 6 in "Questions answered"): Pi 1.2.0 always adds `<cwd>` and `<docs>` — absolute local paths containing the account name — to its system prompt; no CLI flag removes them, and the leak check does not see them; the review loop, the probes and the interactive session are affected as well as the research swarm. The scope question recorded there (all Pi launches vs. research swarm only) carries the recommendation "all, since the mechanism is the same". A plan card was accepted by the maintainer on 2026‑10‑30 with a 2 h phase‑4 appetite (`docs/research/2026-10-30-night-run-plan.md`, lane table and "Lane A"); an implementation on branch `fix/pi-neutral-paths` reached a full green `make verify` once (4419 passed, 2026‑11‑01 08:46 UTC, `docs/journal/handover/2026-11-01-five-lane-night.md`, "Validation") and was then parked on a live defect of its own mechanism (same handover, addendum, lane E): a `before_agent_start` hook that set the prompt option's working directory did not hold on Pi 1.2.0 — the hook receives an already rendered prompt there, so the override changed only later renderings, the launch's own check saw the real directory and failed closed ("no model saw a local path" — the fail‑closed direction worked, the change did not). The tests of that attempt used a fake prompt and missed it. Cause and a proposed fix (rewrite the rendered `<cwd>` section, then test against a prompt rendered by the pinned Pi) are recorded on the bead; nothing was implemented from it. Two red tests were measured on 2026‑10‑31, not five: `tests/test_stage2_swarm.py::test_research_seats_load_neutral_paths` (the repository seat loads no extension) and `tests/test_pi_contract.py::test_real_pi_neutral_cwd_on_every_run` (a 180‑second timeout against the real Pi) (`docs/journal/handover/2026-10-31-night-and-day-run.md`, "Decisions and preferences", the xul8 bullet).

**The pin has moved since the measurement.** `tools/pi/package.json` pins `@earendil-works/pi-coding-agent` at exactly `1.5.0`; `tests/test_pi_contract.py` (`PI_MOVED_PIN`) holds the suite to 1.5.0; the move is the archived change `plans/changes/archive/2026-11-06-pi-catalog-move/spec.md`. Every live measurement of the defect quoted above is from Pi 1.2.0.

**The mechanism in the pinned 1.5.0 source (read from the installed package, not run).** In `tools/pi/node_modules/@earendil-works/pi-coding-agent/dist/core/system-prompt.js`, `buildSystemPromptSections` assembles the structured system prompt and sets `promptSections.cwd` unconditionally (`promptSections.cwd = cwd.replace(/\\/g, "/")`); every section renders wrapped as `<name>…</name>`. The `docs` section (built in the default-prompt branch) embeds `getReadmePath()`, `getDocsPath()` and `getExamplesPath()`; those resolve under the installed package directory (`dist/config.js`, `getReadmePath`/`getDocsPath`/`getExamplesPath` over `getPackageDir()` from `import.meta.url`) — that is `tools/pi/node_modules/@earendil-works/pi-coding-agent/…` inside the checkout, an absolute path that carries the account name and, in a worktree, the worktree name, on every structured system prompt regardless of the launch's working directory. A `project_context` section embeds discovered AGENTS/CLAUDE context files (`renderProjectContext`) only where context-file discovery is on. A `forceSystemPrompt` replaces the whole prompt with opaque section‑free text (`buildSystemPromptState`); an extension's `before_agent_start` handler returning `systemPrompt` sets it (`dist/core/extensions/runner.js`, `emitBeforeAgentStart`), and the same runner hands each handler the normalised `systemPromptOptions` object it then renders from and returns — in the 1.5.0 source an options edit (e.g. of `cwd`) therefore reaches the first rendering, which is what did not hold on 1.2.0. `dist/core/agent-session.js` seeds the base options' `cwd` from the session's working directory (`_baseSystemPromptOptions`). The 1.5.0 CLI (`dist/cli/args.js`, the options help) has no flag that removes the `cwd` or the `docs` section; `--system-prompt <text>` replaces the default prompt (in the builder the custom branch skips the tools/rules/docs sections while `cwd` stays), `--no-context-files` disables AGENTS/CLAUDE loading, and `--no-extensions` explicitly keeps `-e <path>` loads working — the pattern the research seats already use.

**Where Pi is launched today, and with which working directory.** Every model call to the `opencode-go` endpoint goes through Pi: `LAUNCHERS = {"opencode-go": "pi", "claude-code-plan": "claude-code"}` (`scripts/stage2_swarm.py`). The prompt-bearing launches:

- Review‑loop members, `run_reviewer` (`scripts/stage2.py`): `tools/pi/pi --print --no-session --no-approve --no-extensions --no-mcp --no-skills --no-context-files --no-prompt-templates --no-themes --offline` with `--no-tools` (free) or `--tools read,grep,find,ls` (paid), `--thinking max`, `--model opencode-go/<model>`, `--append-system-prompt <file>`; no extension is loaded. The working directory is the scratch directory for free members and `ctx.root` — the worktree root — for paid members (the `dispatch_go` call's cwd argument). A paid reviewer therefore presents the worktree root path in `<cwd>`.
- Research swarm members, `Run.pi_command` (`scripts/stage2_research_run.py`): the same discovery‑off base. Repository seats load the path‑lock extension `-e <scratch>/repository-pathlock.mjs` (source `scripts/stage2_repository_pathlock.mjs`) and return `self.root` (the worktree root) as cwd; public seats load `-e <scratch>/research-tools.mjs` (source `scripts/stage2_research_tools.mjs`) and return the scratch cwd. Repository data travels as an `@file` attachment, not in argv (the comment at the data‑file write).
- Availability probes, `probe_go` (`scripts/stage2_availability.py`): discovery‑off, no extension, scratch cwd.
- Catalog refresh and listing (`scripts/stage2.py`, the free‑stage discovery): `tools/pi/pi update --models` and `tools/pi/pi --list-models`, scratch cwd, no prompt sent.
- Interactive session (`scripts/stage2_session.py`): `cli_argv` transport `pi` runs `--no-extensions --no-mcp --no-skills --no-prompt-templates --no-themes -e <policy copy> --offline --no-approve --model …`; context files stay on deliberately so the session reads the repository's AGENTS.md (comment at the argv build, maintainer 2026‑10‑09). `terminal_command` launches with `cd <root> && exec /usr/bin/env -i …` — the session's cwd is the worktree root. The policy extension `scripts/stage2_session_policy.mjs` registers only a `tool_call` handler today; no `before_agent_start` handler exists anywhere in the runner's extensions. The preflight checks (`--help`, `--list-models`, both `--offline`) send no model request.

The implement, draft and bounded‑explore routes run GLM flash through Claude Code, not Pi (`scripts/stage2.py`, `implement` route table; `model-endpoints.yaml`, the opencode‑go entry's phase notes), so they are outside this mechanism.

**Why the leak check does not see the paths.** `scripts/leakcheck.py` scans the change folder, the tracked/untracked tree as it stands on disk, every reachable commit, the staged diff, and the prompt texts the caller declares ("What is scanned" in its module docstring; `docs/WORKFLOW.md`, the review‑loop section: "The leak check scans what this repository presents, not what else the disk holds"). The `<cwd>`, `docs` and tool sections are assembled inside Pi at request time from the process working directory and the install location — none of them is part of a scanned text. The prompt files the runner declares are clean; the paths are added downstream of the check.

**Where the paths travel.** Every Pi model call goes to the declared `opencode-go` endpoint (`model-endpoints.yaml`, `endpunkte` entry `opencode-go`: operator OpenCode, `darf_sehen: [framework]`), addresses held by the contracts (`tests/test_pi_contract.py`, the `GO_NATIVE`/`GO_MOVED`/`ZEN_SHIPPED` constants). The declaration's `framework` class covers this repository's content; the machine's local paths (account name, worktree name, install path) are what the RS‑3 review flagged as a finding of its own.

**Capture infrastructure that already exists.** `scripts/research_capture.py` is the attended F‑1 capture of the research‑swarm change: a scratch world with canaries, a loopback OpenAI‑compatible mock that records every request (full body, tool schemas, redacted headers), the swarm's real command builders started through `stage2.PI_WRAPPER`, and a verdict computed from what the server recorded ("missing evidence is FAIL, never PASS"). `tests/test_pi_contract.py` starts the real pinned Pi against a loopback stand‑in and fails rather than skips (module docstring). Both are the places where a "no local path reaches the request" evidence path already has its shape.

**Not there in this tree.** Grep over `scripts/` and `tests/` for `<cwd>`, `<docs>`, `before_agent_start` and "neutral" finds no neutral‑path handling: no extension registers `before_agent_start`, no launch neutralises its cwd, and neither red test name of the parked attempt (`test_research_seats_load_neutral_paths`, `test_real_pi_neutral_cwd_on_every_run`) exists — the only "neutral" hits are the unrelated `neutralise_record_markers` (`scripts/stage2_research_run.py`) and its tests.

## What is unclear about it

1. Whether the 1.2.0 defect still exists on the pinned 1.5.0. The installed source suggests the `before_agent_start` options edit now reaches the first rendering (`emitBeforeAgentStart` renders from the same normalised options object it hands the handler), but nothing in this worktree measures a live 1.5.0 rendering. Read, not measured.
2. Whether `--system-prompt` maps to the builder's `customPrompt` (the branch that skips the `docs` section) end‑to‑end, and what else it strips (tools/rules sections) — read in the builder source, not traced through `resource-loader.js` and not run.
3. Whether a custom section named `docs` (the `sections` option) overwrites the built `docs` section — the builder applies custom sections after the built ones, which reads as an overwrite; not measured.
4. What the parked branch holds (rounds of review‑loop work, the two red tests, the saved wip commits) — outside this worktree; not read. The same holds for the bead's recorded cause/fix text: the tracker is not rendered in the tree, so the quotes above are second‑hand from the handovers.
5. Whether the account name or home path is already a leak‑check denylist rule — the denylist lives outside the repository (`~/.config/cc-routing/denylist.txt` per the `leakcheck.py` docstring) and was not read.
6. Whether `pi update --models` sends any local identifiers in its registry/catalog requests — a foreign call without a prompt; not measured.
7. Whether the interactive session's `docs` section paths are reachable in practice (Pi reading its own docs dir when asked about the harness) — behaviour not measured; the paths are in the prompt regardless.
8. The scope question (all Pi launches vs. research swarm only) stands as recorded on the bead with the 2026‑10‑29 recommendation "all"; no newer decision exists in this tree, and the new change folder carries no `spec.md` yet that could declare one.
