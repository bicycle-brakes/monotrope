| SR-1 | BLOCKER | SPEC | base | spec.md AC6, AC5 (and Problem) | [AMBIGUITY] AC6 says full verification is still required before an attempt is accepted, and it counts "cheap green accepts without `make verify`" as a refutation. The runner no longer works that way. Implement and repair run `verify_attempt(mode="targeted")` (`scripts/stage2.py:11094`, `:11672`). When the targeted selection does not fall back, the attempt is accepted after the targeted check alone and `make verify` never runs (`_targeted_body`, `:8155-8190`). `prompts/04-implement.md:10-11` describes the same behaviour. Reading A: every cheap-green attempt, or at least every one that adds a script, must still pass `make verify`. That means overriding the targeted route, which the non-goals rule out ("reuses existing … failure handling without changing architecture"). Reading B: "full verification" means the existing post-run check, which is targeted or falls back to full. Under that reading, AC6's refutation is already red on today's unchanged runner for every targeted accept, so a test written to the criterion's wording fails. AC5 has the same problem: it says "before `make verify`", and its refutation names only full verification or a checkpoint following a red check, not the targeted check. Reason: the spec must describe the runner as it is since the draft of 2026-11-07 | — |

| SR-3 | MAJOR | SPEC | base | spec.md AC5 refutation; AC2 | [AMBIGUITY] AC5 is refuted when "the protected caller failure is absent from the retry prompt". Checks that run earlier can end the attempt first. In targeted implement mode, `new_file_guard` refuses a new production file that no test reaches before any cheap check runs (`scripts/stage2.py:8134-8147`). Inside `cheap_checks`, a ruff failure returns before pytest is even selected (`:7425-7428`). So an attempt that adds an orphan script with no test, or with a lint fault, gets a retry prompt without the caller failure, and AC2's selection is never computed. Reading A: whenever an added script is an orphan, its caller failure must reach the retry prompt. The caller check would then have to run, or be reported, even when the guard or ruff is red, which changes the existing "first red ends the attempt" order. Reading B: the failure is required only when the caller check actually ran. The existing order stays, and an untested orphan script costs two retries: the guard first, then the caller check. The spec does not say which reading holds, or where the new check sits relative to the guard. | Opus | in spec — [DETAIL] decided by the orchestrator: AC5 applies when the caller test is the first failing check; if an earlier check (new_file_guard) ends the attempt first, the caller test still runs in that same check round and its failure is appended to the same retry listing. Reason: the retry must carry every known failure | — |
