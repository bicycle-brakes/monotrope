## Research findings — index-merge-regenerates (phase 1, GLM 5.3 Flash, 2026-10-28, worktree `index-merge-regenerates` at branch `fix/index-merge-regenerates`)

### What exists today

**The doctrine this change is named after already stands.** `docs/WORKFLOW.md` §3, "Pull requests stay mergeable", bullet "Generated files are regenerated": "`plans/INDEX.md` is rebuilt (`scripts/plans_registry.py --index`) on a conflict, never merged by hand (bead coding-harness-hfsz)" (docs/WORKFLOW.md, §3 last bullet block). The same rule in its portable kit form: `templates/agents-mergeable-prs.md`, bullet "Generated files are regenerated. A generated file is rebuilt by its generator on a conflict, never merged by hand" (header comment dates the section to the maintainer, 2026-10-27). The bead id `coding-harness-hfsz` appears exactly once in the tree — that WORKFLOW bullet (Grep `hfsz`, one hit). The opening commit of this change (`2f97d8f6`) files bead `coding-harness-njtm` "with coding-harness-hfsz".

**The generator and its guard.** `scripts/plans_registry.py` has exactly two modes (module docstring): `--check` reports hygiene through `_verdict` without writing, `--index` regenerates `plans/INDEX.md` ("a tool that writes while checking cannot tell whether the tree was right beforehand"). `render_index()` builds the table from every artefact's frontmatter; `INDEX_HEADER` stamps the file "GENERATED by scripts/plans_registry.py --index — do not edit by hand". `check()` ends with the rule's backstop: when the tracked index deviates from `render_index()` the verdict is a **BLOCK** — "plans/INDEX.md deviates from its inputs / Fix: make index" — with the reasoning that index and inputs both move by commit, so the contradiction belongs at its own pull request, not as DRIFT behind `--strict`; a missing index is also BLOCK (`plans_registry.check`, `INDEX.exists()` branch). Note `_frontmatter` returns `None` on unreadable YAML — during a merge with unresolved conflict markers in a sibling artefact, that artefact reports "no readable frontmatter" and its rendered row falls back to placeholder dashes; the regenerate step presupposes the real conflicts are resolved first.

**The gates carrying the guard.** `decisions/gates.yaml`: gate id `plans-registry` (command `python3 scripts/plans_registry.py --check`, job `verify`, enforcement `block`, `needs_tracker: true`, reason names "`make staleness` is the same command") and gate id `plans-registry-strict` (`--check --strict`, job `drift`, `block`). Hosted CI runs both (`.github/workflows/ci.yml`, the two `plans_registry` steps). So a hand-merged index goes red at the next verify or drift run — today the only mechanical detection of a hand merge.

**The second regeneration site — the runner.** `scripts/stage2.py`, `prepare_derived` ("Stamp only changed, held documents, then render the index before verification") runs `plans_registry.py --index` from `trusted_registry` — a scratch mirror whose `scripts/` comes from `git archive HEAD`, so the renderer's code is the committed one while the data is the attempt's (hardening R-19 and the #188 review P2: scratch `HOME`/`TMPDIR`, alias and hardlink refusals on the index path). The living spec `plans/specs/implementation-verification/spec.md` (bead coding-harness-mfv, accepted/done, integrated by PR #102 at merge `2dd8e96f`, 2026-10-08) holds this contract; its criterion 3: stamping precedes index rendering, which precedes `make verify`, on every attempt including retries. Consequence for merges: a branch that merges `main` and then enters any runner phase gets the index regenerated there; a text-only change that never enters the runner relies on the gate alone.

**The merge practice, as recorded.** The daily PR sync is doctrine, not code: `docs/WORKFLOW.md` §3 "Synced daily, automatically" (test-merge via `git merge-tree --write-tree origin/main origin/<branch>`, conflicts "resolved while it is small", bead coding-harness-eq6y). Grep for `merge-tree` finds **no script under `scripts/`** — only WORKFLOW, the kit template, handovers and archived plans — so the sync and its conflict resolution run by hand or by agent. Recorded instances of the regenerate-don't-edit practice: `docs/journal/handover/2026-10-09-remote-session-merges-tracker-and-pi-plan.md` ("#105 and #106 only conflicted textually in `plans/INDEX.md` (generated; regenerated, not edited)", and as a session rule: "`plans/INDEX.md` is generated: resolve it with `python3 scripts/plans_registry.py --index`, never by hand"); `docs/journal/handover/2026-10-23-night-run.md` ("A1 (#228): `origin/main` merged (`2c8cc3ec`, only `plans/INDEX.md` conflicted, regenerated)").

**The named remedy does not exist in this tree.** The Makefile, read in full, defines only `verify`, `test`, `staleness`, `gates`, `leakcheck`, `venv`, `lock` — no `index` target, and `.PHONY` lists the same seven. This is a *declared* bootstrap gap: `docs/WORKFLOW.md` opening note ("Not all of it is here yet", checked 2026-09-30 at `41abf42`) lists "the targets `make change` and `make index`" among the pieces the text names that are not in this repository, with "Where the text below says one of them does something, it describes the target, not this tree" (`docs/WORKFLOW.md`, bootstrap note). Yet two live instructions name it: the check's own remedy line "Fix: make index" (`plans_registry.check`, both BLOCK rows) and the command list `make index # regenerate plans/INDEX.md` (`docs/WORKFLOW.md`, "Verification runs through git and CI"). Grep `make index`: those three hits plus one archived research mention. The invocation that works today is `python3 scripts/plans_registry.py --index`, which is what the handovers and the living spec's practice use. The Makefile header also carries its own constraint for any addition there: nothing in it restates a gate command, and `tests/test_ci.py` pins Makefile and gate list against each other (Makefile header, W-6).
