**What "slip" means — the only in-tree definition.** The test-strategy draft states: "The system tier never runs inside a runner attempt (maintainer, 2026-11-12, answer A): an attempt runs the fast tier and the touched integration tests; the system tier runs before phase 6, in CI and nightly. A fault it finds that an attempt called green is counted as a slip" (`docs/research/2026-11-12-test-strategy-draft.md`, section "Three tiers", end). Its measurement section names the reporting: "The morning handover names three numbers: total tests, full-run minutes, and slips (a fault the targeted check called green that the full run found, bead coding-harness-0swp Q-5)" (same file, "What to measure"). The decision behind it: targeted-check-more-verbs' interview answer of 2026-11-11 — "new code no test reaches, directly or through imports, is refused at once; the runner counts slips in the local run log" (`docs/journal/handover/2026-11-11-day-decisions-six-lanes.md`, "Decisions and preferences", targeted-check-more-verbs bullet). **Not there:** on this branch the word "slip" appears nowhere in `scripts/` or `tests/` (grep returned only unrelated "slips through" comments) — the counter is not implemented here; it exists only in lane 3's unmerged branch.

**The rule the counter serves was decided before the counter existed.** ADR 0025 (`docs/adr/0025-targeted-check-after-repair.md`, accepted, decided 2026-11-08) point 4: "The orchestrator measures repair duration, verify-lock wait and every failure the full check before phase 6 finds that a targeted check missed, over five changes or two weeks, whichever comes first, and reports the result to the maintainer." The slip counter is the mechanism that would make that measurable per run rather than by hand. Point 5 gives the testing-strategy spike (bead coding-harness-1ga5) the right to amend or replace the ADR; the amendment lane 3 drafted is **not merged**, so this worktree holds the unamended 2026-11-08 text.

**The check that can call a fault green — the targeted repair check, as this branch holds it.** `scripts/stage2.py` defines the mode constants `TOOL_SECONDS = 5 * 60`, `VERIFY_SECONDS = 45 * 60`, `TARGETED_PYTEST_SECONDS = VERIFY_SECONDS` (module constants, `scripts/stage2.py:4329-4333`; the targeted pytest limit is its own since #382) and `TARGETED_LABEL = "Runner targeted checks"` (`:4257`). `targeted_selection()` (`:6128`) computes what a targeted repair check covers or returns `full(reason)` with a catalogue of unsafe cases: undecodable git paths, a changed prompt, shared execution infrastructure, shared test configuration (`conftest.py`), links, non-ordinary files, non-Python input kinds, production code with no linked test, the whole `tests/test_stage2.py` until bead coding-harness-vg9 splits it, unreadable checks. `run_targeted()` (`:6287`) runs the selection outside the verify admission; `scope_text()` (`:6229`) and the full-scope line (`:6245` region) are the runner-owned evidence lines — "never 'full green'"; `_targeted_body()` (`:6381`) and `verify_attempt()` (`:6464`) wire it into the attempt, with `verify_mode: str = "full",  # repair: "targeted"; implement keeps the full check` (`:8542` region). On this branch the targeted mode is repair-only — `test_targeted_mode_is_repair_only` (`tests/test_stage2.py:25116`) and the docstring "`mode=\"targeted\"` is the repair's" pin it; the widening to implement and draft (the 2026-11-11 decision) lives on lane 3's branch, not here.

**The check that reveals a slip — the full check before phase 6.** `full_verify()` (`scripts/stage2.py:6343`) is the admitted full check of a repair whose targeted coverage was not safe and of phase 6's boundary; the doctrine requires "One fresh green full `make verify` on the head under review … before phase 6. A red, unstartable or timed-out run stops the review" (ADR 0025 point 3) and "a green targeted repair does not replace that check" (`docs/WORKFLOW.md`, post-run-verification paragraph, around line 1759-1765). So the slip event as decidable today is: a repair whose targeted check was green, followed by a red full check on the same change. The future sources (CI, the nightly system tier) are stated only in the unmerged test-strategy draft, whose ADR does not exist yet.

**The local run log the counter would ride on.** `scripts/verify_duration.py` appends version-1 JSON lines to `verify-duration.jsonl` under `verify_lock.state_root()` — the shared state root outside the repository, local only (module docstring, bead coding-harness-1um6; `EVENT_VERSION = 1` and the event tuple `RUN_START, GATE, RUN_END` at `:60-65`). Its contracts: monotonic-clock seconds, incomplete runs labelled not invented, truncated lines diagnosed, symlinked or non-regular history refused with exit 2 (docstring "Interruption"/"Refusals"). The writer is `scripts/verify_all.sh` (the "Measured durations" block, around `:197-230`, calling `python -m scripts.verify_duration`); the reader is the `report [--run ID]` subcommand. **Not found:** any slip count, miss count or per-change verdict history in the log schema — the events carry gates and verdicts, not what a prior targeted check missed. A different counter exists and counts other things: `scripts/stage2_runs.py` counts loop rows, phase-6 rounds and stage-2 calls **from the change folders**, not from the run log, and has no slip number (module docstring and its "What it cannot count" list).

**The dogfooding constraint this change inherits.** Any change touching `scripts/stage2.py` runs the full check, not a targeted one, until bead coding-harness-vg9 splits the file (`targeted_selection`, the `tests/test_stage2.py` route at `:6199-6203`); the runner step limits are code, not configuration, unless bead coding-harness-twvx (central configuration, parked for redraft) lands first. The pins that restate today's behaviour live in `tests/test_stage2.py` — over twenty `test_targeted_*` functions (`:24509` to `:25458`, plus the doctrine pins `test_repair_prompt_consistently_describes_targeted_verification` `:9913` and `test_repair_verification_doctrine_requires_targeted_and_final_full_checks` `:18133`) — and the run-log pins in `tests/test_verify_duration.py`.
