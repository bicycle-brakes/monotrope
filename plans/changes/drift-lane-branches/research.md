**The vocabulary the name is built from.** A **lane** is defined twice: `docs/orchestration.md` ("What a lane is") — a lane is an ordered queue of changes, each item one bead, one branch and one worktree, one session orchestrating all of them, disjoint files between lanes — and `docs/WORKFLOW.md` (§ "Night runs", "The 30-minute wake", bead coding-harness-7x3c) — a lane is one worktree with the change it serves; the active lanes form the run's watch list, recorded in a run state directory (`lanes.txt`, `busy/`, `lane-watch.log` under `${XDG_STATE_HOME}/coding-harness/night/<run-id>/`). One **branch** per change is rule 1 of `docs/WORKFLOW.md` §3 ("Worktrees — one per change": one change, one bead, one branch, one worktree, one session). **Drift** has a defined technical meaning in this repository: `scripts/_verdict.py` (module docstring, "Three levels for drift tools") fixes the shared vocabulary `INFO` / `DRIFT` / `BLOCK` — `DRIFT` means "the project instance has drifted from the state here", exits 1, blocks only `--strict`, and "belongs in a scheduled run, not at somebody else's pull request", while `BLOCK` is a contradiction between this repository's own artifacts and always blocks at the pull request. Consumers of that vocabulary today are `scripts/kit/probe.py`, `scripts/leakcheck.py`, `scripts/new_change.py`, `scripts/plans_registry.py` and `scripts/ramp_valves.py` (each imports from `_verdict`). Other drift senses in the tree: the `ci-drift` gate (`docs/WORKFLOW.md`, "Local verification" — the committed `ci.yml` is held to the `ci_gates.py` derivation), the address drift of the archived change `plans/changes/archive/2026-11-16-address-drift-warning/` (OpenCode Go call address, closed by ADR 0024 / go-access-point), and the LakeSwitch pin rationale "two copies of one rule set drift" (`ROADMAP.md`, item 2). Which of these senses the change name uses is not decidable from the tree.

**Mechanisms that touch lane branches today.**

- *Freshness at creation.* Rule 3 of `docs/WORKFLOW.md` §3: a worktree is always cut from a freshly fetched `origin/main`, because "a worktree on a stale base produces a pull request that is behind before it opens". Rule 6 retires the worktree and its branch after the merge — "a worktree nobody works in is a place where a later session finds an old state and takes it for the current one"; rule 2 retires sibling directories beside the repository (D-5).
- *The one anti-drift engine, scoped to open pull requests.* `scripts/pr_sync.py` provides two commands over one merge engine (module docstring): `sync` discovers "every open pull request" (`discover()`, one bounded `gh pr list --state open --json …` read, `LIST_LIMIT`) and pushes a merge of fetched `origin/main` with a regenerated `plans/INDEX.md` under an exact expected-head lease; `merge-main` is the supported hand merge for phase-6 preparation and never pushes. The doctrine (`docs/WORKFLOW.md`, "Pull requests stay mergeable", first bullet, bead coding-harness-eq6y) runs the sync **on request** by the day session or night orchestrator — "no scheduler runs it". The structural consequence for lanes: the sync's discovery set is open pull requests, so a lane branch whose change has not opened its pull request yet is outside the one mechanism that merges `main` into stale branches.
- *Protections and reports of the sync.* The sync skips and reports fork pull requests, bases other than `main`, decision pull requests (`decision` label or `decide(` title), branches touching a runner-held or human-decided path, and branches a local worktree holds with uncommitted or unpushed work; conflicts outside the index are reported with their paths and stop that branch; pull requests older than five working days (`WORKING_DAYS_OVERDUE = 5`, `scripts/pr_sync.py`) are listed for the maintainer at the end of every report (`docs/WORKFLOW.md`, "Pull requests stay mergeable", bullets 1–2; behaviour covered by `tests/test_pr_sync.py`, e.g. `test_sync_skips_protected_work`, `test_sync_does_not_update_forks_or_other_bases`, `test_moved_remote_head_is_preserved`, `test_overdue_report_counts_weekdays`).
- *Phase 6 on a current base.* The phase-6 prompt starts with `python3 scripts/pr_sync.py merge-main --root .` (`prompts/06-review.md`, "The base"); `docs/WORKFLOW.md` §1's phase table and "Reviewed on a current base" state the verdict holds only for the commit it saw. GitHub's server-side Update-branch and merge buttons cannot run the helper; the unchanged `plans-registry` gate stays their backstop (`docs/WORKFLOW.md`, "Generated files are regenerated", bead coding-harness-hfsz).
- *Merge-time freshness.* Rule RB-G7: with the merge queue active, a PR is admitted at its exact head (`gh pr merge --merge --match-head-commit`) and counts as merged only when GitHub shows `MERGED`; without the queue, every merge puts the other open PRs behind and each next one is brought up to date with all checks awaited first (`docs/WORKFLOW.md`, "Merging a series, one at a time"; archived change `plans/changes/archive/2026-10-08-rb-g7-merge-freshness/`). Concurrency on hot files is capped at three open PRs, one per foreign-model lane, oldest finished first (same section, bead coding-harness-6y0t), and lanes keep to disjoint files (`docs/orchestration.md`, "What a lane is").
- *Per-worktree precondition, without a main-relation.* `scripts/check_worktree_state.sh` fails closed on a rebase/merge/cherry-pick in progress, a detached HEAD (safe reattach is its only auto-repair), a wrong branch, or a HEAD that moved backward against a recorded min-known sha (its incident class: "a detached HEAD at an OLD review base … the diff it reviews is not the diff that will merge"). It compares a worktree against its own recorded state; it has no notion of distance to `origin/main`.
- *Observation, not verdict.* `scripts/machine_facts.py` (doctrine: `docs/orchestration.md`, "Machine facts at the start of a night run", bead coding-harness-yql7) counts registered non-bare worktrees with "stale registrations counted" — an explicit observation, nothing compared against a floor, nothing cleaned up or refused.
- *No branch check in the wake order.* The night-run wake works a fixed order — rearm, read the lane file, check each lane's job completion/activity and each busy marker's ownership, serve an idle lane, park or complete lanes, append one summary line (`docs/WORKFLOW.md`, "The 30-minute wake" and the wake paragraph) — and no step of it inspects a lane branch's relation to `origin/main`. Lane branches appear in run records only as hand-checked inventory lines: "Every lane branch is committed and pushed, with a clean tree" (`docs/journal/handover/2026-11-19-night-run-2026-11-18-a.md`), "All lane branches are pushed" (`docs/journal/handover/2026-11-16-day-six-lanes.md`), and the lane-branch/head table of the latest morning report (`docs/journal/handover/2026-11-21-night-run-2026-11-20-a-morning.md`, "Open work").
- *A settled decision constrains the after-merge side.* `plans/changes/verify-cheap-before-admission/decisions.md` Q-4 (answered by the maintainer, 2026-11-13): no second mechanism after a merge of `origin/main` into a lane branch — the gates before admission are the one place that catches what a merge introduced; the recorded acceptance is that "the fault shows at the next start of the full check and not at the merge".
- *Gates read the merge-base, not the distance.* The diff base of the interview gate is `merge-base(HEAD, origin/main)` (`scripts/check_interview_minimums.py`, module docstring and `_git` call), `scripts/stage2.py` computes the same merge-base as review diff base (function around `run_git(root, "merge-base", "HEAD", "origin/main")`), and the plans-registry gate uses `git merge-base origin/main HEAD` (`scripts/ci_gates.py`). None of these reports a branch as behind; they only anchor a diff.
- *The origin incident of the existing rules.* On 2026-10-27 five runner pull requests could no longer merge `main` — merge base `f8a6b330` or older, conflicts in `scripts/stage2.py`, `tests/test_stage2.py` and `plans/INDEX.md` (bead coding-harness-s05q; assessment `docs/research/2026-10-27-parked-runner-prs.md`). The rules of "Pull requests stay mergeable" and the portable template `templates/agents-mergeable-prs.md` came from that incident (`docs/WORKFLOW.md`, same section's intro).
- *Summary phrasing differs from doctrine.* `AGENTS.md` condenses the rule as "Pull requests stay mergeable: synced daily, asked about after five working days …", while `docs/WORKFLOW.md` states the sync runs on request with no scheduler (bead coding-harness-eq6y). Both files name the same mechanism; the word "daily" vs "on request" is a difference in emphasis I am reporting, not judging.

Measurement notes also treat lane branches as a distinct population: the route-success study counts only changes merged into `main` and excludes "the lane branches of 2026-11-02" (`docs/research/2026-11-02-route-success.md`, "Method" and "Reading"), and a findings-per-model proposal speaks of "each unmerged lane branch that gained rows" (`docs/journal/handover/2026-11-20-night-run-2026-11-19-b.md`, maintainer item 3 — proposed AGENTS.md wording, not applied).

### What is unclear about it

1. **The bead's description is unreadable from this worktree.** The Dolt database is not hydrated locally and no rendered copy exists in the tree (house rule 2); the id appears only in `plans/INDEX.md` and this folder. Whether `drift-lane-branches` means detecting drift of lane branches (a report), repairing it (extending the sync's discovery to lane branches without pull requests), or retiring drifted worktrees is not decidable from the tree. This is the first interview question.
2. **Which population drifts.** Three candidate populations are distinguishable in the tree: open pull requests (covered by `pr_sync.py sync` on request), lane branches without a pull request (outside its discovery set — the structural gap stated by `discover()`), and registered-but-stale worktrees (counted by `machine_facts.py`, cleaned by hand per WORKFLOW §3 rule 6). Which one the bead targets is not stated anywhere I read. Whether any current lane branch actually sits behind `origin/main` I could not measure: this phase runs no git command and holds no remote state.
3. **The boundary drawn by the answered decision Q-4.** `verify-cheap-before-admission/decisions.md` Q-4 declined a check of its own after a merge of `origin/main` into a lane branch. A drift *report* at a wake or in `machine_facts.py` is a different mechanism from a post-merge *check*, but where the maintainer draws that line for lane branches is unrecorded; the interview should place any new mechanism relative to Q-4 and relative to the `INFO`/`DRIFT`/`BLOCK` levels of `scripts/_verdict.py` (a lane branch is inside this repository, so the docstring's instance-vs-framework split does not directly assign it a level).
4. **Class is undeclared.** The skeleton frontmatter of `plans/changes/drift-lane-branches/research.md` carries no `class:` field, while the runner reads the class from `--class` and the headers of `research.md` and `spec.md` and refuses missing, invalid or disagreeing declarations (ADR 0020 routing; archived specs such as night-stall-guard's carry `class: bounded` as the pattern). The declaration must exist and agree before later phases consume it.
5. **"Synced daily" vs "on request".** Whether `AGENTS.md`'s "synced daily" is a promise the sync's operator must keep or loose condensation of the on-request doctrine is unrecorded where I read; if the change touches the sync's trigger model, this wording difference becomes a decision item for the maintainer (AGENTS.md is the maintainer's file — proposals only, as the 2026-11-19-b handover recorded for an earlier AGENTS.md proposal).
