# Codex drafts spec and plan — Research

Phase 1 for bead coding-harness-rhq, read against `origin/main` on
2026-10-12. Candidate 2 of the research of bead coding-harness-nsm
(`plans/changes/codex-takeover/research.md`): phases 2 (Spec), 2b (Design)
and 3 (Plan) are drafted by Codex instead of Opus 5.5, to save Claude tokens.
So that Codex does not review what it drafted, a Claude model becomes the
stage-2 reviewer of the spec (phase 2a). The maintainer has answered the
first interview question already (2026-10-12, recorded on the bead): a Claude
model takes over phase 2a only; Codex stays the phase-6 code reviewer, since
the code comes from GLM and Codex reviews nothing of its own there.

## Questions for the exploration

1. How `scripts/stage2.py` calls Codex today (`run_codex`, `spec-review`,
   `review`, the `session` verb of ADR 0012): which tools and sandbox it
   grants, whether any call can write files, how the 2a session is recorded
   and resumed in phase 6, and which tests pin that.
2. How phases 2, 2b and 3 run today: the `spec-planner` agent definition
   (`.claude/agents/`), `prompts/02-spec.md`, `prompts/02b-design.md`,
   `prompts/03-plan.md`, their `Model` lines, the validators and gates a
   draft must pass, and the ADR-answer step (`scripts/harness.py decide adr`)
   that runs inside phase 2.
3. Where the routing of phases to models is written: `docs/WORKFLOW.md`
   sections 3 and 4, `model-endpoints.yaml`, ADR 0007, ADR 0011, ADR 0012,
   and `AGENTS.md`; which tests pin the routing text.
4. What a Claude reviewer for phase 2a would need: how `spec-review` builds
   its prompt and writes its rows, what `prompts/02a-spec-review.md` (or its
   equivalent) asks, and how an orchestrator could check a Codex draft before
   the review (the gates in `make verify` that read `spec.md`, `design.md`
   and `plan.md`).

Stage-2 call, 2026-10-12: explore · attempt 1 · route flash · endpoint glm-coding-plan · model glm-5.3-flash · leak check clean over 370 files, 922 commits, 12 rules.

## Runner exploration — 2026-10-12

### What exists today

**How the runner calls Codex (question 1).** `scripts/stage2.py` pins Codex in the constant `CODEX = ("openai-codex", "gpt-6.1-sol", "max")` and starts it only in `run_codex`: the command is `codex exec` — `exec resume <id>` on a resumed call — with `--json`, `-m gpt-6.1-sol`, `-c model_reasoning_effort="max"`, `-c sandbox_mode="read-only"`, `--disable hooks --disable memories`, and `-o <temporary answer file>`, followed by the prompt as the last argument. The child gets an empty standard input, the repository root as its directory (`launch`), and an environment built by `foreign_env` from the allow-list `ENV_ALLOW`, which includes `CODEX_HOME`. The thread id comes from the first `thread.started` JSON event (`thread_id`); a non-zero exit, a missing thread event or an unreadable answer file raises `CallFailed`.

Two verbs call it. `spec_review` (phase 2a) runs `preflight(root, change, CODEX)`, builds the prompt with `phase_prompt(root, "02a-spec-review.md", change)` — the prompt file's full text, then the change line, then the constant `ANSWER_FORMAT` (six-cell rows) and `READ_REQUEST` — records the audit line with `begin_call`, and appends to `findings.md` the block `## Phase 2a — Codex, <date>` with the parsed rows (`answer_block` adds the columns Reviewer = `Codex`, Status = `open`, Broke a test = `—`) and the line `Reviewer session: codex <thread>`. `review` (phase 6) refuses while the loop record has undecided rows, takes the last `Reviewer session: codex <id>` line (`SESSION_LINE`) as the resume target, prompts with `06-review.md` plus "Write only your verdict now.", appends `## Phase 6 — Codex, <date>` with the rows and the line `Phase 6 verdict: codex <thread>, <date>`, states it when no session was recorded or the resume started a new thread, then calls `release` (loop rows into `findings.md`, record deleted) and, when rows were released, makes a second resumed call with `MARK_FORMAT` and fills each row's `Phase 6` cell through `parse_marks` and `fill_marks` (`agree`, `disagree — <reason>`, or `no answer`).

No headless Codex call can write: `sandbox_mode="read-only"` is pinned on every `run_codex` call, first, resumed and the loop-marks call, and the calls receive no file paths. The one Codex path that writes is the interactive `session` verb: `scripts/stage2_session.py` starts `codex` with `--cd <root> --sandbox workspace-write --ask-for-approval on-request`, as ADR 0012 (decision 6) records, and that ADR states the runner does not verify Codex's sandbox. `--stage2-off` is refused for every verb except `explore` and `implement` (`main`). `begin_call` writes a new `findings.md` header with `produced_by: … name: codex` when the endpoint is `CODEX`, otherwise `pi` — no third producer exists. The tests pinning this are in `tests/test_stage2.py`: `test_codex_is_pinned_on_first_and_resumed_calls` (model, effort, sandbox, no `-s`/`--ephemeral`), `test_codex_runs_with_hooks_and_memories_off`, `test_the_codex_prompt_carries_its_phase_prompt_in_full`, `test_the_spec_review_answer_lands_as_codex_rows_with_its_session`, `test_a_failed_codex_call_writes_no_session_line`, `test_review_resumes_the_recorded_session`, `test_a_fresh_phase_6_session_says_so`, `test_no_loop_row_reaches_the_verdict_call`, `test_codex_marks_each_loop_row_after_its_verdict`, `test_a_failed_mark_call_leaves_the_marks_empty`, `test_review_is_refused_while_a_loop_row_is_undecided`, and the ask-rule tests `test_settings_ask_before_codex`, `test_a_missing_or_covered_codex_rule_is_caught`, `test_the_omnigent_render_keeps_the_codex_rule`.

**How phases 2, 2b and 3 run today (question 2).** No runner verb drafts these phases: `VERBS` in `scripts/stage2.py` holds `explore`, `implement`, `spec-review`, `review-loop`, `release-loop`, `review`, `probe`, plus `session` in the argument parser's choices — a drafting verb is not there, which is a different statement from "not found". The phases run in the interactive Claude Code session that `docs/WORKFLOW.md` §3 routes to Opus 5.5 at effort `xhigh` (`claude --model claude-opus-5-5 --effort xhigh`), following the three prompts. `prompts/02-spec.md` names its gate as the interview check plus `python3 scripts/validate_change_artefacts.py --check` plus no open `[DECISION]`, points at `templates/spec.md`, fixes the header fields (`class:`, and for a `feature` `change:` and a quoted `adr_question`), and requires after the spec review that the author works every 2a row into `spec.md` or rejects it with a reason. `prompts/02b-design.md` names `python3 scripts/plans_registry.py --check` as its gate, sets the phase by class (D-14: `architectural` always, `feature` either the phase or one sentence why not, `bounded`/`spike` never), states that nothing checks this rule until the change-artefact validator lands (bead coding-harness-jc3), and describes the ADR draft from `templates/adr.md`, which becomes `docs/adr/<NNNN>-<slug>.md` in the change's own pull request. `prompts/03-plan.md` names `validate_change_artefacts.py --check` as its gate, defines the plan card, the criterion ledger's three entry forms, and the rule that a recorded Stage-1 explore route is copied into `plan.md`, and ends "Then `/clear`".

The `[DECISION]`/`[AMBIGUITY]` prose gates are measured by no script either: a search of `scripts/` for those strings returns nothing. The agent definition the question assumed is also not there: `.claude/agents/` holds seven definitions (code-generation-orchestrator, consistency-auditor, entity-builder, entity-deployer, migration-supervisor, preconditions-gate-runner, reconciliation-orchestrator), none named `spec-planner` and none for spec, design or plan drafting. `templates/` holds `spec.md`, `design.md` and `adr.md`; there is no plan template — the card exists only in `prompts/03-plan.md`.

The ADR-answer step inside phase 2 is `scripts/harness.py`, whose one verb today is `decide adr`: it puts the ADR question of every feature without an answer to the maintainer and writes the answers in the format whose one reader is the gate `adr-answers` (`scripts/check_adr_answers.py`); it works in a terminal or records a stated answer with `--change --answer --reason --stated-in`; it writes answer files and a commit message and never stages, commits or merges; who may answer is the `owner_role` of the `decisions/answers/` entry in `provenance.yaml` (`framework-architect`).
