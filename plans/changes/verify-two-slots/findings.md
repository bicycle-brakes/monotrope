| S2-1 | MAJOR | SPEC | base | `spec.md` criteria 2 and 4; Open decisions, first [DETAIL] | [AMBIGUITY] The spec doesn't say whose capacity applies when live entries carry different `HARNESS_VERIFY_SLOTS` values. Criterion 2 only covers "all new entries" using one value, and criterion 4 has no such condition. Reading A: each entry compares the occupied count with its own value. A `=1` run then enters an empty machine, but a later default entry joins beside it, so `=1` does not mean "run alone". A `=1` waiter at the head of the queue with one slot taken either holds a `=2` waiter behind it (a free slot stays unused) or is overtaken (a later waiter passes a live earlier one); criterion 4 refutes both. Reading B: the lowest value among live holders and waiters governs, kept in shared state, so a `=1` entry keeps the machine to itself for its whole run. Each reading gives different tests for criteria 2 and 4. | Opus | open | — |
| S2-2 | MAJOR | SPEC | base | `spec.md` criterion 2; Open decisions, first [DETAIL] ("consistent values must be supplied to all new entries") | [AMBIGUITY] The spec doesn't say whether `HARNESS_VERIFY_SLOTS` travels to child processes. The memory-floor override does: `inherit_env` copies it explicitly (`scripts/verify_lock.py:771-772`). The runner's allow-list for launched calls holds no `HARNESS_*` name (`scripts/stage2.py:412-425`). Reading A: the setting travels like the floor override, so the operator's value reaches the independent entries the runner and its agents start. Reading B: it does not travel, so an independent entry started under the allow-list (for example an agent's own `make verify`) uses the default 2 while the runner's in-process full check uses `=1`. Criterion 2's condition, "all new entries", then cannot be met by setting the variable once, and a reduction to 1 is not machine-wide. Which processes the operator must reach, and how, is left to the builder. | Opus | open | — |
| S2-3 | MAJOR | SPEC | base | `spec.md` criteria 4 and 10; Open decisions, second [DETAIL] ("FIFO applies among updated waiters") | [AMBIGUITY] The spec doesn't say whether an older single-slot checkout's waiter must ever get in while updated admissions keep overlapping. Reading A: updated waiters ignore an earlier old waiter. The old waiter needs the exclusive lock, and it gets that only if both slots happen to be empty at one of its non-blocking polls every 0.25 s (`verify_lock.py:122`, `:635`). On a busy night an old lane can therefore wait without end: the queue wait has no deadline and uses up no step limit (`verify_run.py:924-925`). Lanes opened before the merge are exactly these. Reading B: updated waiters stay behind an earlier-registered old waiter. A free slot then stays unused, which criterion 4 refutes. Criterion 10 forbids only overlap, so no criterion can fail on either choice. | Opus | open | — |
| S2-4 | MAJOR | SPEC | base | `spec.md` criterion 12 ("run durations", "individual wall times") | [AMBIGUITY] Two measures of a run's length fit the text. Reading A: wall time from launch to exit, including the cheap phase and the admission and memory waits. Reading B: the execution seconds the history records. `run_end.seconds` sums the gate segments and leaves out the queue and memory waits (`scripts/verify_duration.py:16-17`), and criterion 11 keeps wait apart from execution. The machine has 8 GiB, a 25 % floor and 30 s rechecks, so the second simultaneous run's memory gate can hold it for minutes. The same trial can then pass the 1.6× limit under B and fail it under A. | Opus | open | — |
| S2-5 | MAJOR | SPEC | base | `spec.md` criterion 12 ("representative night load"; *Basis:* Q-3 at `b5c2105b`) | The trial's load condition is defined only by answer Q-3 on the unmerged branch `feat/verify-slots`. `research.md` ("What is unclear") says those records cannot be read from this tree, and spec, research and decisions give no process mix, load figure or bound. | S2-8 | MINOR | SPEC | base | `spec.md` criterion 3 | [AMBIGUITY] "Exactly `1` or `2`": the module's own precedent strips the floor override before parsing it (`memory_floor()`, `verify_lock.py:394`).
