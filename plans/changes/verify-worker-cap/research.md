## What exists today

**The verify pytest gate is the only place that spawns workers, and it runs uncapped.** The gate `pytest` in `decisions/gates.yaml` (job `verify`, enforcement `block`, floor `true`, placement `both`) declares the command `python3 -m pytest tests/ -q -n auto`. `-n auto` is pytest-xdist's "one worker per CPU core" mode (the plugin is pinned as `pytest-xdist==3.8.0`, `pyproject.toml` dev group and `requirements-ci.txt`). Nothing in the repository caps that number: I searched the whole tree for `-n auto`, `xdist`, `numprocesses`, `maxprocesses` and `max_workers` and found no `--maxprocesses`, no fixed `-n <int>`, no environment override, and no pytest configuration file at all — `[tool.pytest.ini_options]` in `pyproject.toml` holds only `pythonpath = ["."]`, and there is no `conftest.py` under `tests/`, none at the repository root, and no `pytest.ini`/`setup.cfg`/`tox.ini` (glob checks, this session; the same conclusion is stated in `plans/changes/swarm-test-speed/research.md`, "The suite has exactly one speed lever").

**The command string is pinned in four places that must move together.** (1) `decisions/gates.yaml`, gate `pytest` — the one list (D-10/O-4) every runner derives from. (2) `.github/workflows/ci.yml`, step id `pytest` — generated by `python3 scripts/ci_gates.py --generate-ci`; hand edits fail the `ci-drift` gate. (3) `Makefile`, the `make test` recipe — held whole-line by `tests/test_ci.py::test_the_makefile_runs_what_the_one_list_runs` (W-6), which compares the entire recipe line against the mapping entry `"python3 -m pytest tests/ -q -n auto": "make test"`. (4) `docs/governance/gate-catalog.md`, the pytest row — generated between markers by `scripts/ci_gates.py --catalog` and held two-sidedly by `tests/test_gate_catalog.py` (an independently authored formatter, `_expected_cells`, so a renderer cannot agree only with itself). `scripts/verify_all.sh` holds no command of its own; it substitutes only the `python3` word in each gate command and runs the rest verbatim through `sh -c`.

**`-n auto` is young and its motivation is speed, not parallelism limits.** It was introduced by PR #168 (`perf/verify-xdist`, bead `coding-harness-d5a`), merged 2026-10-19 13:49; before it, the hosted pytest step ran single-process at 294–412 s and the local `make verify` took about 24 minutes (`docs/journal/handover/2026-10-19-optimization-exploration.md`, "The runtime work finished while this session ran" and the numbered next steps; `docs/journal/handover/2026-10-19-night-run-seventh.md`, "Numbers").

**Measured load today.** An isolated full-suite baseline at `dbef390f` on 2026-10-28 ran 4082 passed, 17 skipped in 520.43 s wall with `-n auto` on 8 cores (`plans/changes/swarm-test-speed/research.md`, "Orchestrator addendum"; the same number as "eight workers" in that change's `spec.md`, Problem section). The hosted gate job overall took 6 min 18 s to 8 min 33 s in the 2026-10-18 hosted runs (`night-run-seventh` handover, "Numbers"). The hosted workflow runs on `runs-on: ubuntu-latest` with one Python 3.12 matrix leg and no `timeout-minutes` on the job (`ci.yml` job `gates`; the missing timeout also noted in `swarm-test-speed/research.md`).

**Recorded incidents where the worker count is already visible as a factor:**
- *Memory:* a local kit-probe pytest run with `-n auto` was killed by Claude Code's memory reaper at swap 8.3 of 9.2 GB, judged "probably memory pressure", and not repeated (`docs/journal/handover/2026-10-19-night-run-eighth.md`, bead-7so entry). This was the probe run, not the repository gate — the memory datum is real, its transfer to the gate is not yet measured.
- *Flakiness under xdist load:* the terms change reworked a test driver so its marker "no longer depends on a pipe read within a fixed time under xdist load" (`plans/changes/terms-test-fixtures/decisions.md`, the [DETAIL] row "One shared builder…/The flaky test waits on something load-independent").
- *Interrupt interaction:* the defect behind review-loop-deep-b was "the Ctrl-C test's uncaught interrupt stopped its xdist worker" during a red-first `pytest -n 4` run (`plans/changes/review-loop-deep-b/findings.md`, "Implementation, 2026-10-25"); the fix guarantees the runner kills its whole process group so "a hung `make verify` leaves no shell, pytest or worker behind" (`scripts/stage2.py`, process-group kill in the `verify_attempt` path).
- *Not a parallelism problem:* the 10 errors in `tests/test_pi_contract.py` observed under xdist on 2026-10-19 were reproduced identically without xdist — environmental (missing pinned Pi), per `docs/journal/handover/2026-10-19-optimization-exploration.md`, item 3. This one should not be counted as worker-count evidence.

**Where workers actually start on a verify path today.** Locally, `make verify` → `scripts/verify_all.sh` → gate `pytest` through `sh -c`, one worker per core. Hosted, `ci.yml` step `pytest` on `ubuntu-latest`, same command. The Stage-2 runner (`scripts/stage2.py`) runs `make verify` per implementation/repair attempt and kills the process group on timeout or interrupt; its red-first proof runs pytest **single-process** (the `pytest.main(['-q','-p','no:cacheprovider', …])` call and the `-m pytest -q -p no:cacheprovider -p <RED_PROBE_NAME>` invocation in the red-first section — neither passes `-n`), bounded by `RED_FIRST_MINUTES = 10` (spec criterion 18). The kit probe also runs its generated repository's pytest single-process (`scripts/kit/probe.py`, the `subprocess` list with `-m pytest tests/ -q --tb=no -p no:cacheprovider --junit-xml=…` — no xdist flag).

**What is not there (searched, absent):** a worker cap, a worker-related environment variable, or any xdist configuration anywhere in the tree. `docs/WORKFLOW.md` does not mention xdist or `-n auto` at all (grep over `docs/WORKFLOW.md`, `tools/kit/**`, `tools/claude-code/**` returned no matches), so the workflow doctrine carries no text a command change would contradict.
