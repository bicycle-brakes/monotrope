| S-1 | MAJOR | SPEC | base | Terms "Clean and pushed"; AC5; AC6 | [AMBIGUITY] What counts as a "configured upstream". The house creation command in `docs/WORKFLOW.md` §3 rule 2 (`git worktree add -b <branch> .claude/worktrees/<name> origin/main`) sets the branch's upstream to `origin/main` under Git's default `branch.autoSetupMerge`. It stays that way unless the branch is pushed with `-u`. Reading A (literal): `origin/main` is a configured upstream, so AC5 applies. Once the PR lands as a merge commit, `origin/main` is ahead of the tip, so the worktree is never eligible. Reading B: "upstream" means the remote branch the work was pushed to. An `origin/main` upstream then falls to AC6, and the worktree is eligible once merged. For worktrees made the house way, A keeps nearly every merged one and B removes them. | Opus | in spec — [DETAIL] decided by the orchestrator: an upstream of origin/main (the house creation command sets it) is not a branch upstream; pushed means the branch's own remote ref origin/<branch> exists, or existed and is gone after a merged PR (S-2), and the local tip equals or is behind it. Reason: the creation command's default must not count as pushed | — |
| S-2 | MAJOR | SPEC | base | AC5; AC9; AC12; Open decisions [DETAIL] | [AMBIGUITY] A merged PR's head branch is deleted on the remote, so the branch still has a configured upstream but its remote-tracking ref is gone (`[gone]`). Reading A: this is the "configured but unreadable upstream" of Open decisions, so the worktree is kept, possibly every merged worktree whose head branch was auto-deleted. Reading B: a gone upstream is the normal state after a merge, so `origin/main` ancestry decides. The outcome also depends on what the "fresh fetch" fetches, which the spec never says. A fetch of `main` only leaves a stale `origin/<branch>` that AC5 would compare against, and AC9's "stale evidence" names only merge evidence. Reason: the merged PR is the evidence the work landed | — |
