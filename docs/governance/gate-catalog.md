# Gate catalog

This page is the readable view of the one machine-gate list,
[`decisions/gates.yaml`](../../decisions/gates.yaml) (D-10). The list is the
artefact; this page adds no gate, no enforcement level and no policy — it
renders the inventory so a reader can see what measures, where, and how hard,
without parsing YAML. [`scripts/ci_gates.py`](../../scripts/ci_gates.py) is
the one reader of the list, and `tests/test_gate_catalog.py` holds the
committed inventory to its rendering: a row that drifts from the list —
missing, extra, duplicated, or changed in any displayed field — fails the
suite.

The inventory between the markers is generated, never typed by hand:

    python3 scripts/ci_gates.py --catalog

Run it and paste its output between the markers whenever the gate list
changes. `floor` is the non-negotiable set (a `yes` gate is red when it
cannot measure); `placement` says where a gate measures — `hosted` only in
the hosted CI, `writer` only on a writer machine, `both` everywhere. A
command reads as the command a developer would type; a hosted action is
marked as such, and where a local equivalent exists, the equivalent is named
next to it. The `reason` column is copied verbatim from
`decisions/gates.yaml`; a reason still in German is translated there, at its
source (bead coding-harness-yim).

## Before enabling a gate

A gate is sensible, proportionate and more than an end in itself. These three
questions are the checklist `docs/WORKFLOW.md` §2 points to; a gate that
fails one of them is not enabled, and an enabled gate stays on the list only
while it still passes them.

- **Sensible** — it guards an error that has happened here or is one decision
  away, and a violation is decidable without taste: a check either holds or
  it does not.
- **Proportionate** — the harm it prevents is bigger than the cost it adds to
  every change it touches; a report or advisory level is the honest answer
  while the finding stock it would raise is not yet cleared (see `docs-links`
  and `markdownlint` above for gates living at that level).
- **More than an end in itself** — it serves the workflow's promises
  (artefacts, provenance, one account of verification), not its own green
  run.

What a check detects, and what refutes it: a gate measures a concrete input —
a file, a tree, a tracker render, a hosted branch state — and its red run is
a finding about that input, not a verdict about the change as a whole. What
refutes a gate is the counter-check that plants the fault it guards against
and shows the run going red; a check that was never red measures nothing.
