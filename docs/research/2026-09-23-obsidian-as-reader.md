# Obsidian as a reader of this repository — recommendations

Based on a read of the repository on 2026-09-23 (`main` and the local branch
`docs/obsidian-architecture-view`), written first as a note in the
maintainer's vault and moved here on 2026-09-27. Each recommendation carries
its status at `main` `4e7ea5c`, re-checked on 2026-09-27. Nothing was changed.

## What already fits

- 45 of 66 tracked Markdown files carry frontmatter with a common core
  (`title`, `category`, `status`, `created`, `last_reviewed`, `provenance`,
  `review`, `tags`); `scripts/check_docs.py` enforces it wherever frontmatter
  exists. Counted on 2026-09-27; the first read counted 35 of 57.
- Links are relative Markdown links throughout (142 counted on 2026-09-27), no
  wikilinks: they work the same on GitHub and in Obsidian.
- `plans/INDEX.md` is generated by `scripts/plans_registry.py`, not typed.
- `templates/` carries no frontmatter on purpose (`provenance.yaml`:
  `frontmatter: none`).

## Recommendations, by benefit

### 1. A machine-readable head for handovers

The current state lives in prose sections (*Where we are*, *Next step*,
*Needed from the maintainer*, *Open work and blockers*) and is overtaken by
addenda at the end. A reader that parses only the sections then shows stale
state; one example was a *Needed from the maintainer* entry in lakeswitch that
an addendum had already closed. Proposal for `scripts/handover_schema.py`:

```yaml
summary: "Two sentences on what this session achieved"
next_step: "One concrete next step"
needs_maintainer:
  - "A decision or action only the maintainer can take"
blockers:
  - "…"
```

Rule: frontmatter is the current state, the body is the history; an addendum
also updates these fields. Open question: how this fits `record_sha256` and
`acknowledged_by`.

**Status at `4e7ea5c`:** open; `handover_schema.py` has none of these keys.

### 2. Frontmatter for ADRs

The ADRs carry none, so the register lacks status and provenance.
`provenance.yaml` lists `docs/adr/` with `frontmatter: optional`. Proposal:
`status`, `date`, `supersedes` or `superseded_by`, `provenance:
human-decided`, `bead`; the list under the H1 stays as a readable head or is
generated from it.

**Status at `4e7ea5c`:** open; ADRs 0001 to 0005 have no frontmatter.

### 3. `review` available as a flat field

`review:` is a nested object. Obsidian's properties view does not show nested
objects cleanly, and whether Bases can filter on them is uncertain; test in a
worktree first. If not: either an additional flat `review_status` (then
`check_docs.py` must check that both agree, so there stays one list) or the
register shows review only through the index.

**Status at `4e7ea5c`:** untested.

### 4. Beads visible in a repository vault

Beads live only in the tracker. A render target that writes to
`docs/_render/beads.md` (ignored by git, not excluded in Obsidian) would show
them in the repository map without breaking ADR 0004, because nothing is
committed. The same render could feed the maintainer's personal index.

**Status at `4e7ea5c`:** open.

### 5. Obsidian as a versioned adapter

Instead of settings by hand: `tools/obsidian/` with `app.json` (Markdown
links, relative paths, excluded folders, "update links on rename" off,
because renames run through git or an agent and `check_docs.py`),
`bookmarks.json` (an overview) and a `make obsidian` that copies them into the
worktree's `.obsidian/`. That fits the architecture: a thin adapter, rebuilt
per tool.

**Status at `4e7ea5c`:** open; there is no `tools/obsidian/`.

### 6. A unique display instead of renaming

Repeated file names (`research.md` in every change folder, `_INDEX.md` twice,
`2026-09-17-omnigent-first-target.md` in architecture and in handover) are a
convention; do not rename them. Show `title` and `file.folder` in Bases
instead.

### 7. Small items

- Fix the status vocabulary per `category` (mixed today: `current`,
  `accepted`, `pending`, `proposed`, `superseded`) and check it in
  `check_docs.py`.
- Bring the three research files without a date prefix, or with underscores
  (`Lake-Switch-Architektur-arc42.md`, `Migrationsplan_…`, `arc42_…`), to
  `YYYY-MM-DD-slug.md`, so they sort like the rest.

**Status at `4e7ea5c`:** both open.

## Order

1 and 2 first, because they make a summary, a board and a register reliable
at all; then 5, then 4; 3 only after the test in a worktree.
